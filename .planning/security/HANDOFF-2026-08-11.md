## Two findings that change the plan

**A. Attribution is more broken than the CEO plan stated.** New users never even see the page that holds the referral logic. `handle_new_user()` sets `role='client'` on every signup, and both `AuthCallback.tsx:52` and `Login.tsx:47` only route to `/onboarding/role` when `!profile?.role`. So a new user is auto-sent to `/onboarding/client` or `/trainers`, `RoleSelect` never renders, and neither referral nor UTM attribution ever runs. Removing the dead `if (!profile?.role)` gate inside RoleSelect would fix nothing. Attribution has to move to a path that actually runs for every new signup (server-side in `handle_new_user` reading a ref code from signup metadata is the robust option, and it also fixes the in-app-webview cookie problem). This is an auth-flow change affecting every new user, so it needs eng-review, not a 2am hack.

## The fraud chain, restated (why Phase 1 gates the campaign)

A single trainer account today can: call `create_booking_atomic` with `p_trainer_payout: 5000` (browser-supplied), self-`confirm` the booking with no payment (UPDATE policy allows it), self-`complete` it, and produce a $5,000 payable balance against $0 collected. Only your manual Release stands between that and a real Stripe transfer. Harmless with 7 known trainers; the exposure opens the moment you recruit 25 strangers. That's why the lockdown lands before the first episode, not after.
